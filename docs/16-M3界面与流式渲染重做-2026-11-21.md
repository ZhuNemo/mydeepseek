# 16 · M3 界面与流式 Markdown 重做（2026-11-21）

本轮三件事，起因不同、落点不同：

1. **界面**：M3 只做到"配色换了、控件换了"，但圆角、顶栏、设置页、加载态都还是老形状，
   参照 June 的观感重做；
2. **流式 Markdown**：按上游 SimpleChat 作者给出的排版优化策略重做渲染管线
   （见其 `SmoothReveal.kt` / `LiteralParagraph.kt` / `StreamingProse.kt` 那份说明）；
3. **排查"对话中突然卡死后闪退"**：找到并修掉了**一类**会直接打死进程的缺陷，
   但**没有**复现用户报告的那一次，结论见 §16.5。

> ⚠️ 本轮**没有本地构建**（本机无 JDK 17+ / 无 Android SDK）。所有结论来自读码与
> 依赖产物核对，编译与单测由 GitHub Actions 验收。哪些是"已验证"、哪些是"待验证"，
> 每节都写明了。

## 16.1 流式 Markdown：把每帧的工作量从"整篇"压到"尾块"

上游那份说明的核心不是"降频"，而是**降低每一帧必须完成的工作量**。四条对应的改造：

### ① 逐字显示（`ui/markdown/SmoothReveal.kt`，重写）

| 项 | 旧实现 | 现在 |
|---|---|---|
| 节奏来源 | 固定 32ms 一拍，每拍放 30% 积压 | **按真实帧间隔** `withFrameNanos` 分配预算 |
| 速度 | 无基准，完全由积压决定 | 基础 60 字/秒（60Hz 屏约一帧一字）+ 积压追赶 |
| 追赶 | 32ms 放 30% | 每 70ms 吃掉当前积压的一半 |
| 空闲 | 每 10ms 轮询一次字符串 | `snapshotFlow` 等内容真变化才醒，追平即**挂起** |
| 冷却 | 帧耗时×2，上限 **2 秒** | 帧耗时×2，上限 **96ms** |
| 系统关动画 | 不判断 | `ValueAnimator.areAnimatorsEnabled()` 为 false 时直接给全文 |

上限从 2 秒收到 96ms 是这一条里最要紧的改动：2 秒的冷却在长回答里就是"卡一次、
停更两秒"，观感上等于卡死；96ms 只是短暂让出一点帧给触摸与滚动。

### ② 显示进度提升到**整条回复**（`MarkdownWithMath.kt`）

带公式的回复会被 `splitMath` 切成 `文本 / 公式 / 文本 / …`。旧实现把
`MarkdownText`（自带逐字显示）逐段调用 —— **每段都从头浮现一次**，公式后面那段
会先消失再一个字一个字长出来。

现在 `MarkdownWithMath` 自己调 `rememberSmoothReveal`，再把已揭示的前缀切段交给
内部的 `MarkdownBody`（只渲染、不采样）。切段只是"切窗口"：前面的段文本不变、
命中缓存、连重组都跳过。

### ③ 普通段落绕过第三方库（`ui/markdown/LiteralParagraph.kt`，新增）

流式尾块绝大多数时候就是一段普通中文。走库要：解析成 AST → 建 `AnnotatedString` →
跑 `ExtendedSpans` → 组件树排版。其中前两步对一个没有语法的段落是纯开销。

判据 `isPlainParagraph()` **刻意保守**（判错的代价是原始 Markdown 语法露在屏幕上）：

- 单行；
- 行首不是 `# > - + * \` | ~ <`，也不是 `1.` / `1)`；
- 行内不含 `* _ \` [ ] \ $ | ~`；
- 不含裸链接（库里会把 `https://…` 变成可点链接，纯 `Text` 不会 —— 否则定稿瞬间变蓝，
  正是"版式跳一下"）。

三个前提同时满足才走：**流式尾块** + **没有搜索高亮**（高亮是库的 ExtendedSpans 画的）
+ 判据通过。字号/行高/对齐都取 `markdownBodyStyle`，与库的 `paragraph` 同源，
所以定稿那一刻交回库渲染**版式不变**。

上游那条"新追加字符淡入 150ms"**没有照搬**，原因写在这里（本轮试过并撤掉）：

- 先写成"每次追加起一段 150ms alpha 动画"：流式每帧只追加一到三个字，动画每帧被打断 ——
  最新那几个字永远接近透明、一帧后又突然变实，尾巴在闪；
- 再改成"按位置渐变"（新内容顶部最淡、往下恢复）：最新的那几行会在两三行的窗口里
  都是半透明的，慢速流式下等于**看不见刚写出来的字**。

而逐字显示本身已经给出"字在长出来"的观感。所以这一条路的全部收益就是
"省掉库的解析与建串"，不再往上叠加效果。

### ④ 高度下限：代码块例外（`MarkdownBlocks.kt`）

"高度只增不减"是给半成品语法的（未闭合的 `**` 会让同一段字重新排版、高度变矮）。
但代码块的展开 / 收起**本来就要变高度**：钉住之后收不回去，留一大片空白。
现在尾块含 ` ``` ` / `~~~` 时不套这个下限。

### ⑤ 预热（`MarkdownText.kt`）

- 「尾部消息超过 2.4 万字就不预热」的规则**删掉**：那不是省掉工作量，是推回主线程
  （首帧同步解析 → 卡住）。现在**长消息也预热**，只预热首帧要用的
  `MarkdownInitialBlocks` 块。
- 内部两道上限：**48 块** / **24k 字符**；每块之间 `ensureActive()` —— 换会话 /
  翻走时立刻停手，不留一个还在解析几十万字的孤儿协程。
- 与渲染走**同一条**归一化 + 切块路径（`normalizeForMarkdown` → `splitBlocksCached`），
  缓存 key 逐字相同才能命中。

### ⑥ `splitMath` 快路径（本来就已具备）

`MathSplit.kt` 开头就有"不含 `$` / `\[` / `\(` 时原样返回"的分支 —— 与上游
`displayMathSegments` 同样的优化，本轮确认无需改动。

### 已验证 / 待验证

- **已验证（读码）**：所有调用点都走新的三参 `renderBlock`；`warmMarkdownCache` 的两个
  调用处都在 `withContext(Dispatchers.Default)` 里，改成 `suspend` 不需要改调用方。
- **待验证**：真机上的出字节奏（60 字/秒 + 70ms 半衰期是本轮新调的参数，
  上游给的是它的取值，不是我们的实测值）；`DstIn` 蒙版在低端机上的绘制开销。
- 单测：`SmoothRevealTest`（冷却上限 96ms）、`LiteralParagraphTest`（判据的保守性）。

## 16.2 界面：把"像 M3"补成"是 M3"

### 形状阶梯（`ui/theme/Theme.kt`）

之前一直用 Material 默认档（4/8/12/16/28），那套是按高密度工具类应用调的。
新增 `SimpleChatShapes`：**8 / 12 / 16 / 24 / 28**，并接进 `MaterialTheme` ——
对话框、浮层、卡片等**所有**走 `MaterialTheme.shapes` 的组件一次性对齐。

### 排版（`ui/theme/Type.kt`）

补上 `headlineMedium`（28sp Bold，基准值）/ `headlineSmall` / `labelLarge`。
大标题直接取这一档，字号仍受全局 `TypeScale` 约束（与正文一起等比缩放）。

### 顶栏（`ui/chat/TopBar.kt`）

- 高度 56 → **64dp**（M3 Small top app bar 的规格），标题用 `titleLarge`；
- 两侧动作改成**填充式圆形图标按钮**：48dp 触控区 + 40dp `surfaceContainerHigh` 色块。
  不能把底色画在 48dp 那层 —— 按钮会比标题高出一截，水波纹也会从色块边缘溢出来。

### 空态（`ui/chat/EmptyState.kt`）

图标从"裸放的 44dp 线框"改成坐在一块 **96dp / 32dp 圆角**的 `surfaceContainer` 色块里。
空白页面需要一件有体积的东西压住。

### 设置页（`ui/settings/SettingsScreen.kt`）

- **大标题 + 填充式圆形返回键**（M3 Large top app bar 排法：返回键在上、标题下一行左对齐）；
- **分组标题用主色**（`labelMedium` 13sp）：分组标题承担导航、不承担正文，
  灰色小字在一屏十几行里读不出来；
- **卡片 24dp 圆角**，行间分隔改成 **2dp 的页面底色缝**（M3 的 connected list 观感）——
  不是一条 1dp 细线。`inset = 16.dp` 的调用点仍保持"细线 + 缩进"，
  那是对话框里的列表分隔线，与上面的"缝"是两种东西。

### 加载指示器（`ui/common/ContainedLoading.kt`，新增）

形态是 M3 Expressive 的 **contained loading indicator**：容器圆角在"正圆 ↔ 圆角方"
之间往返（1100ms 一个来回），里面一颗点绕中心匀速转（2600ms 一圈）。两者周期
刻意不成整数比，避免周期性"对齐"。

**为什么自己画**：本项目 `compose-bom 2026.09.00` 解析到的 material3 是 **1.4.0**，
而 `ContainedLoadingIndicator` 在 1.4.0 里**不存在**。核对方式：

```bash
curl -s https://dl.google.com/dl/android/maven2/androidx/compose/compose-bom/2026.09.00/compose-bom-2026.09.00.pom \
  | grep -A2 material3          # → <version>1.4.0</version>
unzip -l material3-android-1.4.0.aar | grep -i loading   # 只有 LoadingIndicatorTokens，没有组件类
```

用在两处：「等第一个 token」（18dp，配过程文字色）与「切会话」（48dp，主题色）。

### 待验证

- 全部界面改动**未经真机/模拟器目视确认**（本轮无构建环境）。风险最高的是
  `SettingsTopBar` 的高度变化 —— 一级页与六个二级页共用它，若某页标题过长会走省略号。
- `SettingsCard` 的"缝"用 `settingsBackground`（= `scheme.surface`）绘制。若将来把
  卡片色改成比页面更深，缝仍然成立；但若两者同色，缝会消失（届时改成
  `surfaceContainerLowest` 之类的更暗一档）。

## 16.3 排查：一类会直接打死进程的缺陷（已修）

### 症状与真因

用户报告"和 AI 对话过程中突然卡死后闪退"。本轮**没有拿到那一台设备的日志**，
所以不能说"这次修的就是那次闪退"。但读码时找到一处**确定**会让你看到
"点一下 → 卡半秒 → App 没了"的缺陷，性质与症状一致：

> `viewModelScope` 默认**没有** `CoroutineExceptionHandler`。协程体里抛出的异常
> 会被交给线程的默认处理器 —— 在 Android 上就是**进程直接死掉**。

而下面这些操作此前都是**裸 `launch`**，一条 `SQLiteException`（磁盘满、库被写锁）
或 `IOException` 就能带走进程：

| 位置 | 操作 |
|---|---|
| `ChatViewModel.retryMessage` | 重试 |
| `ChatViewModel.regenerate` | 重新生成 |
| `ChatViewModel.continueMessage` | 续写 |
| `ChatViewModel.deleteMessage` | 删除消息 |
| `ChatViewModel.forkFrom` | 从这里新建对话 |
| `ChatViewModel.switchVariant` | 切版本 |
| `ChatViewModel.clearCompaction` | 清除压缩摘要 |
| `HistoryViewModel.*` | 重命名 / 置顶 / 删除 / 批量置顶 / 批量删除 / 播种预设 |

对比之下 `send` / `editMessage` / `compactContext` 一直有 try-catch —— 也就是说
**同一个应用里两条写库路径的容错标准不一样**，而缺的那一半恰好都在"对话中会点"的位置。

### 修法

`launchGuarded(tag) { … }`：取消照旧往外抛（那是正常控制流），其余异常收成
一条 banner（新增文案 `error_action_failed`，中英各一条）+ 一条带 tag 的日志。

抽屉那一侧不直接持有 banner，`HistoryViewModel` 暴露一个 `error: StateFlow`，
由 `RootScreen` 转投到对话页那条 banner —— 复用同一套提示，而不是再造一个 Snackbar 宿主。

另外，`continueMessage` 失败时会把那条消息从 `STREAMING` 退回原状态：
否则它会以"正在生成"的样子卡在界面上，而 `actionable = !streaming` 会让
操作栏与长按菜单**全部禁用** —— 删不掉、切不走（§44 记录过的"僵尸消息"同一个坑）。

### 另一处（已修）

`ChatScreen` 的消息索引用 `produceState(…, vm.messages.size, …)` 重建。
切版本 / 重新生成后条数**可能一点没变**（换的是同父的兄弟），但 id 与下标都变了 ——
索引里留着已经不存在的 id，点一条就跳错位置。现在把 `vm.pathRevision` 也作为 key。

## 16.4 看了但**没改**的地方（如实记录）

| 位置 | 情况 | 为什么不动 |
|---|---|---|
| `ChatRepository.loadActivePath` | 把活跃路径**全部**正文读进内存（文档 §5 已列为 P1） | 要改成分页加载，等于重做消息列表的数据源；本轮无法验证，风险远大于收益 |
| `prepareRequestAttachments` | 每次发送把历史所有图片读回 base64，请求对象同时持有全部 | 同上：属请求组装的结构问题，不是一行能改的 |
| `MermaidDiagram` | 每张图一个 WebView（各解析 3.4MB mermaid.js），销毁延迟 800ms | 删除延迟是为了绕开 `GLFunctorDrawable` 的 SIGSEGV（§47 记录）；贸然改回会更糟。要根治得改成"一张图一张位图"的离屏渲染 |
| `MarkdownStateCache` | 40 万字符 AST 缓存 | 预算本身合理（十几条长回复），不是内存大头 |
| 语音 / 朗读链路 | `AudioTrack` / TTS 的异常已有 `runCatching` 与超时兜底 | 未发现新问题 |

### 关于"卡死后闪退"的下一步（需要设备侧证据）

App 自带崩溃诊断（设置 → 诊断 → 导出崩溃诊断）。下次复现请导出该文件，
能直接区分三类原因：

1. **OOM**（`java.lang.OutOfMemoryError`）→ 指向 `loadActivePath` / 图片 base64 / WebView；
2. **未捕获异常**（本次修的那一类）→ 栈顶会指向具体 repository 方法；
3. **ANR**（`/data/anr/`，需要 `adb bugreport` 或开发者选项里的"ANR 追踪"）→
   指向主线程在解析 / 排版 / 主线程 IO。

三者对应的修法完全不同，没有这份证据时只能做"缩小可能性"的改动，不能声称根治。
