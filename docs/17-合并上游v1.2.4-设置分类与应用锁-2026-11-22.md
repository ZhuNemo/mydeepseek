# 17 · 合并上游 v1.2.4、设置页分类重构与应用锁（2026-11-22）

> 本文记录一次**大跨度合并**：上游从 v1.1.5 走到 v1.2.4（246 个文件、约 2.2 万行），
> 同时按需求重做设置首页、新增整机应用锁。合并方式、取舍理由、以及**尚未验证**的部分
> 都写在下面 —— 结论以 CI 为准，不以本文为准。

---

## 17.1 为什么不是普通的 `git merge`

我方仓库与上游仓库的提交历史**不是同一条**（同一个作者仓库被重建过，提交哈希对不上），
所以 `git merge` 会当成两条无关历史，冲突到几乎每个文件。

采用的办法是**三方合并（three-way merge）**，基线取上游 `v1.1.5`（我们上次合入的版本）：

| 角色 | 内容 |
|---|---|
| base | 上游 `v1.1.5` 的树 |
| ours | 本仓库当前（v1.2.2） |
| theirs | 上游 `v1.2.4` 的树 |

逐个文件按 `git merge-file` 规则合并，得到：

- 只有上游改过 → 直接取上游（41 个）
- 只有我方改过 → 保留我方
- 双方都改 → 165 处冲突，逐个判断
- 我方没有、上游有 → 直接取上游（新增 90 个源码文件）
- 我方删过、上游又改过 → 恢复上游版本（33 个，含分享、上下文压缩等）

## 17.2 冲突的处理原则

不是"谁新听谁的"，而是按**改动性质**分：

| 类别 | 处理 | 例子 |
|---|---|---|
| 上游重写过的功能文件 | **整份取上游**，我方改动作为小补丁重贴 | `ChatScreen`、`ChatViewModel`、`MessageList`、`MarkdownText`、`SettingsScreen` |
| 我方独有的功能 | 保留我方，并按上游新 API 适配 | 保险箱、WebDAV 同步、写库异常收口（`launchGuarded`）、`refreshFromStorage` |
| 设计系统 | 保留我方 | 主题、配色、形状阶梯、`Controls` / `Dialogs` / `ContainedLoading` |
| 双方都只是新增 | 两边都留 | 字符串、设置项、DAO 查询 |
| 上游已演进出更好的实现 | 取上游 | `NetworkErrors.networkText`、`SseClient` 重试、`Attachments` 的 `initialIndex` |

### 取上游的代价（必须说清）

`ChatScreen` / `MessageList` 整份取上游后，v1.2.2 里针对这两个文件的 M3 接线
（顶栏参数、空态调用、胶囊按钮尺寸）被上游版本覆盖。设计系统本身还在
（`Controls`、`TopBar`、`EmptyState` 都是合并后的版本），但这两处的**调用点**
按上游写法走。这是用"能编译"换"观感完全一致"的取舍，后续可以再逐点对齐。

## 17.3 排除跨对话记忆

按需求，**跨对话记忆整块不合并**。删掉的东西：

- `ui/chat/CrossChatMemory.kt`（检索实现）与其单测、仪器测试
- `ChatViewModel` 里的检索、注入、每会话开关
- `ChatRepository.memorySessions / memoryMessages / setConversationMemoryEnabled`
- `ChatDao` 的两条记忆查询与两个投影类
- 设置里的「记忆」页、会话面板里的「记忆对话」开关、相关文案
- `SettingsStore` 的 `crossChatMemory / crossChatMemoryLimit`

**保留**的：`conversations.memoryEnabled` / `drafts.memoryEnabled` 两列。

> 为什么不删列：这两列一旦写进 Room schema，删掉就要重建表；而 `conversations`
> 带着指向 `messages` 的级联外键，重建过程中任何一步出错就是**整库消息消失**。
> 留一列不读不写的布尔值，代价是一个字节；删列的风险是丢数据。

## 17.4 数据库：版本 10 → 14

上游把 schema 推到 13（用量、生图标记、记忆开关），我方原来自己的版本号也叫 10
（加 `hidden`）。两条线在这里交汇：

```
9 → 10  上游：messages.tokens_cache_hit
10 → 11 上游：messages.imageGeneration
11 → 12 上游：messages.imageRequest
12 → 13 上游：conversations/drafts.memoryEnabled
13 → 14 本仓库：conversations.hidden
```

⚠️ **13 → 14 必须容忍列已存在**：我方老用户（旧版本号 10）的库里 `hidden` 早就加过了，
再 `ALTER TABLE ... ADD COLUMN` 会报 `duplicate column name`，迁移失败 = 启动即崩。
所以这一条迁移先查 `PRAGMA table_info`，有就跳过。

## 17.5 设置页：分类是导航，不是内容

改造前的一级页是"三张卡 + 十来行"，主题、语言、主题色、预设、字号、两个对话开关、
朗读音色、数据、API 交错排在一起。改造后一级页**只有十个入口**：

| 分组 | 入口 |
|---|---|
| 常用 | 外观 / 对话与输入 / 朗读 / 预设 / 工具与服务 |
| 数据与安全 | 数据与同步 / 安全与隐私 / 用量与余额 |
| 其他 | 诊断 / 关于 |

每行只回答两件事：这一类是什么、**现在是什么值**（主题模式 · 主题色、锁定方式、
当前 API 名称、预设条数……）。具体开关全部收进二级页 —— 与系统设置、June 这类客户端的
通行结构一致：**分类是导航，不是内容**。

被移动的项：

- 「语言」从一级页 → 「外观」页（它本来就是"界面看起来怎样"的一部分）
- 「账户余额」从一级页 → 「用量与余额」页（那里本来就有余额查询，一级页那份是重复的）
- 新增「安全与隐私」页：应用锁、解锁方式、自动锁定、修改密码、保险箱入口

## 17.6 应用锁：整机，不只是保险箱

### 解锁方式

| 方式 | 实现 | 说明 |
|---|---|---|
| 不锁 | 默认 | — |
| 自定义密码 | 6 位数字 + PBKDF2 | **与保险箱共用同一把** |
| 与屏幕锁定相同 | `KeyguardManager.createConfirmDeviceCredentialIntent` | 交给系统验证，本应用拿不到任何凭据 |

没有引 `androidx.biometric`：它的入口是 `FragmentActivity`，而本应用是 `ComponentActivity`，
接进去要改基类；`createConfirmDeviceCredentialIntent` 是系统自带的"验证设备凭据"入口，
用户设了指纹就用指纹、设了图案就用图案，连"未录入指纹"的分支都不用自己写。

### 什么时候锁

- **冷启动**：一律先解锁。首帧 `stored == null` 时**什么都不画** —— 先画内容再被盖住，
  那一帧对"我锁了应用"的人来说就是泄露。
- **回前台**：`ON_STOP` 记时间，`ON_START` 与设置里的超时比较（立即 / 1 分钟 / 5 分钟）。
  用 `ON_STOP` 而不是 `ON_PAUSE`：下拉通知栏、来电横幅的 `ON_PAUSE` 不代表人离开了。
- **兜底**：选了 PIN 但从没设过密码 → 视为不锁；选了"与屏幕锁定"但设备没设锁屏 →
  有密码退回 PIN，没有就不锁。否则人会被自己的设置关在门外，只能清数据。

### 键盘手感（对齐 June 的做法）

- 按键按下缩到 0.88，用 `spring()` 回弹，不是线性动画；
- 每输一位，对应圆点放大到 1.45 倍并**变成圆角方**，再弹回圆形（morphing）；
- 输错时整排按键从左到右依次抖一下（28ms 错峰）+ 拒绝触觉；
- 退格长按清空；
- 输满自动提交，留 100ms 让最后一位的圆点动画走完。

### 与保险箱的关系

两者共用同一把 PIN。整机锁开着时，解锁后进保险箱**不再要求再输一次** ——
同一把密码连输两遍不增加安全性，只是摩擦。整机锁关着时，保险箱保持原有的独立解锁
（它防的是"手机借给别人时被顺手翻"）。

## 17.7 顺带修掉的一个真 bug（保险箱）

旧实现用 `LaunchedEffect(entry, stage)` 提交 PIN，按"值有没有变"触发。
用户输错后**重输同一个密码**时，`entry` 与上一次完全相同 → Effect 不重跑 →
"第二次输对了却没反应"。现在改成挂在提交回调上，每次提交都会执行。

## 17.8 已知未验证项

本文所有结论都来自**静态检查**（资源引用、图标符号、括号闭合、悬空 import），
**没有在本机编译过**（本机只有 JDK 11、无 Android SDK）。因此以下都待 CI 验证：

1. 首次编译是否有类型/签名错误；
2. 迁移 `13→14` 在老库上的实际行为；
3. 应用锁的 `KeyguardManager` 调用在 Android 8–15 上的表现；
4. 上游新功能（生图、余额、诊断、首次引导）与本仓库定制的相互影响。

**发布前必须以 CI 绿为准。**

## 17.9 CI 结果：已全绿（2026-11-22）

上面 17.8 的第 1、4 项已由 GitHub Actions 验证通过：编译、815 个单元测试、Release APK
构建、产物命名与上传全部 success（`main` 与 `v1.3.0` 两条流水线均绿）。第 2、3 项属于
真机行为，CI 覆盖不到，仍需装机验证。

定位过程中 CI 一共报了三轮错，都是**合并时漏取上游改动**或**测试没跟上实现**，与应用逻辑无关：

| 轮次 | 失败点 | 根因 | 修复 |
|---|---|---|---|
| 1 | 编译 `SmoothRevealTest` | 测试调用 `cooldownAfter()`，但合并后实现用的是上游的 `adaptiveCooldownMs()` | 测试改名对齐实现 |
| 2 | 编译 `SmoothRevealTest` 后再编译 | AAPT：v27 主题覆盖了不存在的父样式 | 早前已删，此轮实为上面同一处的连锁 |
| 3 | 4 个单元测试 | ① `SseLineParser` 漏了上游的 `finishReason → Stopped` 事件；② `ReplyTimelineView.citationMark` 还是旧的上标格式 | 两个实现文件整段对齐上游，两个测试文件同步为上游版 |

另外发现 `DeviceRegression.kt`（androidTest）里还挂着已删除的 `CrossChatMemoryRegression`
引用，一并清掉（CI 的 `testDebugUnitTest` 不编译 androidTest，但留着是隐患）。

CI 定位期间曾临时把失败日志提交到分支（`ci-unit.log`），日志取到后已彻底删除，
工作流也恢复为正式配置（只跑 `main` 与 `v*` tag，不再跑临时合并分支）。

### 一个工作流自身的坑

分支构建时"给 APK 起个可读的名字"这一步会失败：原脚本用 `GITHUB_REF_NAME` 当版本号，
分支构建时那是分支名，产物名会变得奇怪。改为从 `build.gradle.kts` 读 `appVersionName`，
分支与 tag 构建就都能过了。
